AVR controller

Message shapes, output ports and settings for a Denon receiver. Power, main zone, source and bounded volume in dB, each confirmed from the receiver’s own reports.

home-avr-controller1 input · 3 outputshome automation

One receiver. One command owner.

Owns explicit power, main-zone, source and bounded volume commands for a Denon AVR. In the palette it is home-avr-controller; on the canvas it shows its name, or “<area> AVR controller”.

Looking for wiring?

Follow Home theatre for the TCP connection to the receiver and how a theatre activity drives it.

Inputs

Requests and receiver reports arrive as msg.avr. A theatre activity controller sends msg.theatreCommand with target: "avr"; your flow routes it here as msg.avr.

msg.avr shapes
kindOther fieldsUse
intentrequestId, generation, power, sourcepower: "on" with a source name from Sources; omit source to keep the current input. power: "standby" stops the receiver.
volumerequestId, mode, valueDbmode: "absolute" sets the volume; "relative" changes it by a positive or negative amount.
observedlineOne protocol line from the receiver, typically line: msg.payload from the TCP input.
startupNoneAfter a deploy: discard stale observations and query the receiver. A volume request still pending fails with reason restart.
refreshNoneRe-read the receiver without disturbing work in flight. With no request (requestId null, generation 0: the activity controller’s probe after a start with nothing saved) and none of its own, it queries the receiver, then answers on output 2 with msg.theatre = {kind: "target_observation", target, observedAt, values}, where values is {power, source, mainZone} (its input only once it is on), and commands nothing.
msg.status from a Status nodeMQTT out’s “connected”Taken as the startup message (msg.avr = {kind: "startup"}), so the node announces itself again once the broker can take it. Wire in a Status node whose scope is your MQTT out node. Any other status message is ignored.

With publishing on, an MQTT message on home/<area>/receiver/volume/set is also accepted on the input (see below).

Outputs

Three output ports
PortMessageConnect to
1 · Denon commandsmsg.payload (a protocol command as a buffer) with msg.avr_command.A TCP output node to the receiver.
2 · State and resultsState plus ready, failed, rejected, superseded and volume results; while it has a request, msg.theatre = {kind: "target_state", target: "avr", requestId, generation, status, observedAt, details}.Straight back to the theatre activity controller’s input, or a debug node.
3 · MQTT publicationsRetained state, availability and Home Assistant discovery, when switched on.An MQTT out node.

A ready state is stamped with the oldest receiver reading the request relies on, and a refresh is answered once the receiver reports again.

Volume in dB

Volume is in dB: requests (valueDb), bounds, results, published state and the Home Assistant number. The node converts for the receiver, whose own 0-98 scale has 80 at 0 dB, so 0-98 maps to −80 to +18 dB, in half steps. A numeric string counts as a number.

  • Requests are clamped to Minimum volume (dB) and Maximum volume (dB). Bounds must be half-step values between −80 and 18 dB, with the minimum below the maximum.
  • Relative requests resolve from a fresh observed volume, and rapid ones accumulate against the pending target.
  • A request completes on fresh MV evidence from the receiver; ownership is then released, so a later physical or external change becomes the new baseline instead of being corrected.
  • A request with value in the receiver’s own 0-98 was removed in 6.0: it is answered volume_rejected with reason removed-volume-value, and the node logs a warning once per deploy.
  • A theatre activity owns power and source, not volume: a volume request waits while power or source is switching, and is rejected with receiver-not-ready while the receiver is off.

The contract example volume-ownership.mjs shows relative requests accumulating and ownership released after confirmation.

The editor also carries minVolume and maxVolume, the 0-98 bounds of a node saved before 5.0. They were removed in 6.0: a node with only those is an invalid configuration naming the dB setting to set, and saving it with dB bounds clears them. New nodes use node-based Home Assistant identifiers (idScheme = "node"), an internal marker set when the node is added from the palette, not an editor setting.

Optional MQTT and Home Assistant

Off unless switched on, and then named after the Area. Everything goes on output 3. The node announces itself once the flows have started, and again at kind: "startup".

Published state and incoming requests
TopicDirectionPayload
home/<area>/receiver/power/stateOutput 3 · retainedON or OFF.
…/source/stateOutput 3 · retainedThe source name.
…/volume/stateOutput 3 · retainedThe last volume read from the receiver, in dB.
…/availabilityOutput 3 · retainedonline or offline.
…/volume/setMQTT in → controllerA volume in dB from the Home Assistant number.

With discovery on, Home Assistant gets a power binary sensor, a source sensor and a volume number in dB between the two bounds, in 0.5 dB steps. Wire an MQTT in node on …/volume/set into this node. Sets arriving within 0.3 seconds of each other are settled to the last, which becomes an ordinary absolute volume request, bounded and confirmed like any other and never sent to the receiver directly. See Home Assistant.

Status

The node status shows the controller’s phase and a short text: grey ring while discovering, grey dot when idle, blue dot while transitioning, green dot when ready, yellow ring for a manual override, red ring when failed. An invalid configuration, such as 0-98 bounds without dB bounds, is shown on the status too.
