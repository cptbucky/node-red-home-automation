TV, projector and screen as one display

Owns Sony Bravia TV power, projector lamp power and projector-screen position for the modes off, tv and projector. In the palette it is home-display-mode-controller; on the canvas it shows its name, or “<area> display mode”.

Switching between the TV and the projector is make before break: for the projector, the lamp starts and warms up, then the screen opens, and the TV goes to standby last; for the TV, it comes on before the projector shuts down and the screen closes. If the projector fails to start, the TV is left on. A projector warming up or cooling down finishes before a newer request changes it.

Looking for wiring?

Follow Home theatre for how a theatre activity routes its display commands to this node and reads its results back.

Inputs

Everything arrives as msg.display. A theatre activity controller sends msg.theatreCommand with target: "display"; your flow routes it here as msg.display, as the example activity flow does with a switch node and a change node.

Outputs

The TV, the screen and an optional power meter are reached directly over their own network APIs, so only the projector’s infrared toggle leaves the node as a command.

Three output ports

1 · Projector IR fallbackmsg.payload = "power" with msg.display_command: the projector power toggle.Your infrared transport, commanded directly, never through Home Assistant.
2 · State and resultsObserved state plus ready, manual-override, failed, rejected and superseded results, and msg.theatre target state.Straight back to the theatre activity controller’s input.

The editor also carries projectorMeterHost, the meter host’s name before 5.0. It was removed in 6.0 and is no longer read: a node naming only that key is an invalid configuration, in the editor and after a deploy, until Projector power meter host is set. Saving the node with the new host clears it.

Projector power

With a meter host, the node reads the Shelly switch itself. Without one, report the projector from any meter or adapter: msg.display = {kind: "observed", device: "projector", power: "on"} with "on", "standby" or "transitioning" in lower case, or a meter’s reading as watts: 140, read against the on and standby watts.

A power meter node, such as a zigbee2mqtt power node on the projector’s plug, wires straight in: its msg.power = {kind: "observed", watts} counts as the projector’s reading. Wire output 3 back into it, and the node asks it for a reading when it needs one.

A smart plug’s own ON and OFF describe its socket, not the lamp, so send its power in watts instead. A lamp "transitioning", or watts between the two thresholds, keeps its last settled state while it warms or cools.

The node needs a fresh projector reading at every request and while it confirms a change, and asks for one on output 3. Leave output 3 unwired only if the meter reports on its own at least once every Query timeout milliseconds, whether or not the power changes. A device that hasn’t reported within the query timeout is asked again, up to Maximum idempotent attempts in all; then the request fails with reason no-reading, naming the device. This applies to every device.

Query timeout × Maximum attempts

Keep Transport timeout milliseconds below Query timeout milliseconds × Maximum idempotent attempts (5000 × 2 with the defaults), so a slow device’s answer arrives before it is given up on.

Screen viewing position

  • Set: projector mode opens the screen to that percentage of its travel and confirms it within Screen position tolerance.
  • Empty (the default for a new node): the screen’s own open command, confirmed when the screen reports itself fully open. This also suits a screen not calibrated for positions. A node saved with a position keeps it.
  • Other modes close the screen with its own close, which runs to the end and restores a position the screen has lost.
  • A viewing position needs a screen that knows where it is: one that doesn’t is closed first, and if it still has no position, the request fails with reason screen-not-calibrated. Calibrate the screen, or clear the viewing position.

Manual changes

An unsolicited physical change after the display is ready latches manual ownership. The node observes and reports it without corrective commands; a newer activity intent resumes automation.

Status

The node status shows the controller’s phase and a short text: grey ring while discovering, grey dot when idle, blue dot while transitioning, green dot when ready, yellow ring for a manual override, red ring when failed (with the mode and failure reason). An invalid configuration, such as a missing host, is shown on the status too.

MQTT and Home Assistant

This node publishes nothing over MQTT itself. Display state reaches MQTT and Home Assistant through the theatre activity: see Home theatre and Home Assistant.
