Theatre activity controller

Message shapes, output ports and settings for the node that owns the whole theatre’s activity. One request drives every target, and the activity is ready only on fresh evidence from each one.

On this pageOne activity. Five targets.InputsOutputsSettingsActivity profilesWhen an activity is readyStartup and recoveryStatus
home-theatre-activity-controller1 input · 2 outputshome automation

One activity. Five targets.

Owns the theatre’s latest-request-wins activity state, such as tv or off. It turns an activity intent into one semantic command per target (display, AVR, source, lighting and backlighting) and aggregates the generation-scoped target_state evidence each target controller reports back. It never talks to a device: each target controller and its transport do that.

In the palette it is theatre activity controller under home automation; on the canvas it shows its name, or theatre activity when unnamed.

Looking for wiring?

Follow Home theatre for the state contract, the routing switch and the target controllers around this node.

Inputs

Every input is msg.theatre with a kind. A message without msg.theatre, such as a target controller’s own msg.avr or msg.display events on the same wire, is ignored, so each target controller’s output 2 can be wired straight back here.

msg.theatre kinds
kindOther fieldsUse
intentrequestId, generation, activity, optional requestedAtStart an activity. activity must be a configured profile, generation a positive integer. Usually comes from the theatre state contract’s output 1.
target_statetarget, generation, status, observedAt, optional classification, failure, detailsA target controller’s progress. Reports for another generation are ignored.
startup, refreshNoneAsk every target to report again. With no activity in hand it probes the targets and starts recovery.
recoverreason (startup or manual_override), observationsPhysical evidence per target, {observedAt, values}, for adopting an activity without commands.
tickoptional generationSent by the node itself on its timer; you don’t need to send it.

Target status is one of discovering, transitioning, confirming, ready, waiting_for_source, failed or unavailable. A classification of manual_override or drift marks a change the theatre didn’t make.

An intent is a duplicate only of the request in hand: the same requestId, generation and activity sends no commands. A different request whose generation is already taken gets the next free generation when its number is newer than any proposed before (as after a recovery); otherwise an older generation is rejected as stale-generation, and the current one as request-conflict or generation-conflict. Nothing remembers earlier requestIds, so an older one sent again with a new generation is a new request.

Activity intent · msg.theatre
{
  kind: "intent",
  requestId: "example-request-1",
  generation: 1,
  activity: "tv"
}

Outputs

The port order is fixed. Commands go out on output 1; everything the theatre knows goes out on output 2.

Two output ports
PortMessageConnect to
1 · Semantic target commandsmsg.theatreCommand = {target, kind, requestId, generation, …}. kind is intent or refresh; the rest is the profile’s values for that target.A switch on theatreCommand.target (display, avr, source, lighting, backlighting), then a change node per target that moves it to msg.display, msg.avr, msg.sourceCapability, msg.activityLighting or msg.backlighting.
2 · Activity state and eventsmsg.theatre: first a complete {kind: "state", …} snapshot, then any events.The theatre state contract’s input, which publishes the snapshot as retained MQTT state.

The snapshot carries area, requestId, generation, desiredActivity, requestedAt, currentActivity, phase, availability, transitionStartedAt, transitionCompletedAt, targets, failure, degraded and metrics. availability is unknown, available, degraded or unavailable.

Events after the snapshot have kind ready, failed, waiting_for_source, manual_override, drift, superseded, rejected, recovery_required, recovery_adopted, recovery_unknown or recovery_ambiguous, each with area, requestId, generation, activity.

A refresh carries the activity’s values.

A refresh command holds the same wanted values as the intent, so a target controller that started with nothing saved can adopt them and read its device instead of staying idle.

Activity profiles

Each activity name is lowercase, starting with a letter (a-z, digits, _, -). Each profile defines all five targets. Display and AVR values are passed through to their controllers; source, lighting and backlighting are checked.

Profiles JSON · from the example flow
{
  "off": {"display": {"mode": "off"}, "avr": {"power": "standby"},
          "source": {"action": "deactivate", "readiness": "optional"},
          "lighting": {"profile": "off"}, "backlighting": {"power": "off"}},
  "tv":  {"display": {"mode": "tv"}, "avr": {"power": "on", "source": "shield"},
          "source": {"action": "activate", "sourceId": "streamer", "readiness": "required"},
          "lighting": {"profile": "tv"}, "backlighting": {"power": "on"}}
}
  • source.action is activate or deactivate; activate needs a sourceId. A deactivate without one is sent the previous activity’s source.
  • source.readiness is required (the activity waits for the source) or optional (a missing source only degrades it).
  • lighting.profile names a profile in the activity lighting controller.
  • backlighting.power is on or off.

When an activity is ready

Display, AVR and backlighting are required: each needs a fresh ready report. A fresh failed or unavailable report from one of them fails the activity. Lighting is always optional, and the source is optional or required per profile; an optional target that isn’t ready shows in degraded instead of blocking, as does lighting that is ready without lights that never reported (reason unobserved).

A required source that isn’t ready holds the phase at waiting_for_source. A fresh manual_override report from any target puts the theatre in manual_override without corrective commands; a newer request resumes automation.

Once ready, a target that is only due for re-confirmation keeps the activity ready and shows as stale in degraded. An unanswered refresh is re-sent up to three attempts in all; after that the target is reported as not responding (no-response) and is still asked once per freshness window.

Startup and recovery

On startup with an activity in hand, it refreshes every target and confirms again. Without one (a redeploy or restart with no context store), it sends probe refreshes to every target, emits recovery_required and enters recovering.

The display, AVR, source and backlighting controllers answer a probe, when they have no request of their own, by reading their devices and reporting what they show on their output 2, which already goes back to this node: msg.theatre = {kind: "target_observation", target, observedAt, values}, in the profiles’ terms (display {mode}, from the display controller’s own modes; AVR {power, source, mainZone}; source {action: "activate", sourceId} for the one active source, {action: "deactivate"} when all are inactive, or {}; backlighting {power}). Once all four have answered, or the probes run out, it recovers from them, as from a msg.theatre = {kind: "recover", reason, observations} message, which still works. When the fresh display, AVR, source and backlighting evidence matches exactly one profile, that activity is adopted without commands (recovery_adopted). After a start with nothing saved, a target that can’t be asked, such as a backlight that only reports when it changes, needn’t answer: once the probes run out, the controller recovers from the targets that answered, provided the display and the AVR are among them (they tell activities apart, and both can always be read) and exactly one profile matches every target that answered. A target that didn’t answer is unobserved: the activity is ready with it listed in degraded (reason unobserved) until it reports. With no evidence, or more than one match, the activity is unknown, the phase is idle and nothing is commanded until the next request (recovery_unknown), so a restart never switches a running activity off.

After a cold start, the devices say what is running.

Wired as in the example, the theatre shows the activity the devices are in within seconds of a restart with nothing saved, and commands nothing. Lighting isn’t read: an adopted activity leaves the room’s lights as they are. A file context store still keeps the activity, and its counters, across restarts.
