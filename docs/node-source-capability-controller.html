Source capability controller

Message shapes, output ports and settings for the node that decides when a playback source is really ready. An input selection alone never counts as success.

On this pageReady means evidence.InputsOutputsSettingsSource capabilitiesRetries, failure and manual changesStatus
home-source-capability-controller1 input · 2 outputshome automation

Ready means evidence.

Coordinates configured playback sources, such as a streamer or a games console, from what each one can do: whether it can be switched on or off by command, only by a person, or not at all, and which evidence proves it ready. It holds no source names, entity IDs or transport logic; a separate adapter in your flow talks to the device.

In the palette it is source capability controller under home automation; on the canvas it shows its name, or source capability controller when unnamed.

Looking for wiring?

Follow Home theatre, where the theatre activity controller sends this node its source commands.

Inputs

Every input is msg.sourceCapability with a kind. A source ID is lowercase, starting with a letter, and must be configured in Source capabilities.

msg.sourceCapability kinds
kindOther fieldsUse
intentrequestId, generation, sourceId, actionRequest activate or deactivate. sourceId may be null only for a deactivate, which is then reported unavailable (unknown-active-source).
observedgeneration, sourceId, status, observedAt, optional application, playbackThe adapter’s reading. status: active, inactive, available, unavailable or unknown. playback: playing, paused, idle, buffering, stopped or unknown.
command_resultgeneration, sourceId, ok, optional reasonThe adapter’s result for a command. ok: true starts confirmation; it is not confirmation.
refreshoptional requestId, generation, sourceId, actionFrom the theatre activity controller: re-read the source, or adopt the activity’s wanted values after a start with nothing saved. With no request (requestId null, generation 0: the activity controller’s probe after a start with nothing saved) and none of its own, it observes every source that can be read (sending observe with requestId null and generation 0; an observation with any generation answers it), then answers on output 2 with msg.theatre = {kind: "target_observation", target, observedAt, values}, where values is {action: "activate", sourceId} for the one active source, {action: "deactivate"} when all are inactive, or {}, and commands nothing.
startupNoneRe-observe the request in hand with a deadline; the activation itself is never replayed.
tickgenerationSent by the node itself on its timer.

The theatre activity controller’s source command (moved from msg.theatreCommand) already has this shape; its extra target and readiness fields are not used here.

Adapter observation · msg.sourceCapability
{
  kind: "observed",
  generation: 1,
  sourceId: "streamer",
  status: "active",
  observedAt: "2026-01-01T12:00:00.200Z",
  application: "player.example",
  playback: "paused"
}

Outputs

The port order is fixed.

Two output ports
PortMessageConnect to
1 · Semantic source commandsmsg.sourceCommand = {sourceId, operation, requestId, generation, attempt}; operation is activate, deactivate or observe.Your source adapter, which carries out the operation and answers with command_result and observed messages.
2 · Theatre target statemsg.theatre = {kind: "target_state", target: "source", requestId, generation, status, observedAt, details, sourceId, action}, with classification and failure when set.The theatre activity controller’s input.

details holds observedStatus, readiness (each evidence layer: required, available, active, application, playback, satisfied), recovery and metrics (attempts, retries, fallbackUsed).

Source capabilities

Each source has activation, deactivation and confirmation, and may set fallback: true, which is reported as fallbackUsed once a command is sent to it.

Source capabilities · from the example flow
{"streamer": {"activation": "command", "deactivation": "command", "confirmation": "active"}}
  • command: the node sends the operation on output 1.
  • external: someone else switches it; the node only observes and waits (waiting_for_source).
  • unavailable: it can’t be done; the request is reported unavailable (unobservable-source or unsupported-deactivation).
Confirmation evidence
confirmationReady when the observation shows
availablestatus available or active
activestatus active
applicationstatus active and an application
playingstatus active and playback playing
unavailableNever; the source can’t be confirmed

A deactivate is confirmed by status inactive. An unavailable observation reports the source unavailable (adapter-unavailable).

Retries, failure and manual changes

A failed command_result or a confirmation timeout retries the command until Maximum attempts, then fails with the adapter’s reason, command-failed or confirmation-timeout. A reading that stops matching after the source was ready is a person’s change: it is reported as manual_override and never corrected. A ready source is re-read on refresh without leaving ready.
