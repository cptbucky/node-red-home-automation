Releases and upgrading

Which Node-RED and Node.js versions the package needs, how its versions are numbered, and what each major version changes and asks of you. The GitHub release notes have the detail of every release.

Supported versions

The package needs Node-RED 5.0.0 or newer. From 6.0.0, it also needs Node.js 24 or newer.

Supported versions
PackageNode-REDNode.js
6.x5.0.0 or newer24 or newer
5.x5.0.0 or newer22.9 or newer

Node-RED 5 itself runs on Node.js 22.9 or newer; from 6.0.0 this package asks for 24. Check your Node.js version before you update the package.

How versions are numbered

  • Major: the first number

    Everything a flow, a saved node or an installation must act on: for example, raising the Node.js version the package needs, or removing old units or setting names.

  • Minor: the second number

    New nodes and features.

  • Patch: the third number

    Fixes.

An old form, such as an old unit or setting name, keeps working through the rest of its major series, with a warning in the log where it can. It is removed in the next major version. This page has a section for each major version; minor and patch releases are described in the GitHub release notes.

How to upgrade

  1. Read before you update.

    Read the section below for each major version you cross, the supported versions, and the GitHub release notes for the releases in between.

  2. Update the package.

    In Node-RED, open Manage palette and update @avantics/node-red-home-automation there. Or, from your Node-RED user directory, install the version you want and restart Node-RED.

  3. Pin the version you use.

    Name the exact version, so a later install doesn’t move you on before you have read its notes.

  4. Check your flows.

    Open and save the nodes the notes mention, and look for nodes marked invalid and warnings in the log.

Terminal · from your Node-RED user directory
npm install @avantics/node-red-home-automation@<version>

Each GitHub Release also attaches the package tarball and its SHA-256 checksum, which Manage palette → Install → Upload module accepts.

Version 6

6.0 takes circadian lighting out of the room controller into its own node, the circadian lighting policy, which sends rooms the style to use. The room controller applies whatever style it is sent, and a light can be marked on/off only. The room controller also stops speaking Zigbee2MQTT: it sends each light neutral commands through an adapter, the new zigbee2mqtt light node, whose messages to the light are byte for byte what the room sent before, and passes each light’s readings to activity lighting. 6.0 also gathers every change that asks something of you: it needs Node.js 24, takes only true or false on enable inputs, removes what 5.0 deprecated, and no longer lets code import the package’s files. Each of these shows itself, as an invalid node or a warning in the log, rather than failing silently.

It also brings what was added since 5.0.0: the zigbee2mqtt cover and shelly switch nodes, discovery announced as the flows start, and a Shelly script that keeps a detached wall switch working without Node-RED.

When you upgrade from 5.x

  • Migrate every room lighting controller. A room saved before 6.0 is an invalid configuration, and its lights don’t respond, until you migrate it. In its edit dialog, click Create Zigbee2MQTT light nodes to add and wire a zigbee2mqtt light per light (a light whose topics weren’t Zigbee2MQTT’s is flagged, to set up by hand on the neutral light contract). Add a circadian lighting policy, copy the room’s old circadian, sleep and schedule settings into it (the room’s edit dialog lists them), move any Home Assistant switches, set topics and flows that changed circadian lighting or sleep over to it, then click Done, which keeps only each light’s id in Targets JSON. A room that should stay unstyled needs only the light nodes and that last step. A flow that filtered the room’s output by the old command topics must now take the light nodes’ output. Follow the step-by-step migration in the README.
  • Update Node.js to 24 or newer before you update the package.
  • Send true or false to enable inputs: the motion policy’s area-enabled, global-enabled and pause, and the circadian lighting policy’s circadian and sleep messages. Strings such as "ON" are refused with a warning. Home Assistant’s own ON and OFF on the …/set topics still work.
  • Mark a person’s change with manual: true. An intent’s values alone no longer make a light manual.
  • Replace what 5.0 deprecated (see Version 5): Zigbee2MQTT’s brightness and color_temp in intents and activity lighting profiles, the receiver’s 0-98 volume, and the display controller’s old projector meter setting.
  • Code that imports the package’s files directly now fails: only the nodes are a public interface. Installing and using the nodes is unchanged.

Deprecated, removed in the next major version

The 6.0.0 notes deprecate nothing.

Version 5

5.0 separates the decisions from the devices they drive. Requests to lights and the receiver use plain units (percent, kelvin and dB) instead of Zigbee2MQTT’s brightness and mireds and the receiver’s 0-98 scale, so the decisions no longer depend on one kind of device. The display controller’s settings are named by role, and the projector’s power can come from any meter. It also adds the shelly cover adapter, and fixes theatre recovery and screen handling.

When you upgrade from 4.x

  • Lighting values: send brightnessPct (0-100) and colorTempKelvin in lighting intents and activity lighting profiles. Brightness 64 becomes 25%, and color_temp 400 becomes 2500 K (1,000,000 ÷ mireds). 0% is the dimmest level, not off.
  • Receiver volume: send valueDb in volume requests (80 on the receiver’s 0-98 scale is 0 dB). Open and save the AVR controller to store its volume bounds in dB, and update any flow or automation that reads the published volume, which is now in dB.
  • Display controller: open and save it to store its renamed settings. Without the built-in power meter host, wire its new third output to ask your meter for the projector’s power, unless the meter reports on its own at least once every query timeout.
  • Screen: a saved viewing position must be above 0 and at most 100, or empty; with none, the screen opens fully with its own command.
  • Code that imports the package’s files directly: the display transport moved to dist/lib/transports/display-transport. Only the nodes are a public interface.
