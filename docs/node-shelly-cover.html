Neutral commands in, Shelly MQTT out

The shelly cover node (type home-shelly-cover; canvas label: its name, or “shelly cover”) translates a cover controller’s neutral commands into the device’s MQTT control commands, and the device’s status reports into neutral cover readings. It has no broker connection of its own: device messages arrive from an MQTT in node, and its publications leave through an MQTT out node. No function nodes, no Home Assistant and no HTTP.

Looking for wiring?

Follow Wire a shelly cover, then Wire a cover for the controller side.

Inputs

One input takes both the controller’s commands and the device’s MQTT messages. Anything else is ignored.

Input messages
FromMessageEffect
Cover controller, output 1msg.cover_command = {operation, position, generation, …}set_position, stop and observe are translated (see device topics). Other operations, including open and close, are not translated.
MQTT in on <prefix>/#<prefix>/status/cover:<id>The cover’s full status: a new reading.
MQTT in<prefix>/events/rpcNotifyStatus changes for this cover are laid over the last full status; NotifyFullStatus replaces it. Only a change of position, state or calibration makes a new reading.
MQTT in<prefix>/onlinetrue or false: availability.

Outputs

Two output ports
PortMessageConnect to
1 · To the devicemsg.topic and text msg.payloadAn MQTT out node on the same broker, with no topic set.
2 · To the cover controllermsg.cover = {kind: "observed", position, motion, observedAt}, {kind: "availability", online} or {kind: "command_result", generation, ok: false, reason}The cover controller’s input.

Position runs 0 (closed) to 100 (open), as the controller’s does; set invert on the controller if yours runs the other way. Motion is opening, closing or stopped (the device’s open, closed and stopped all read as stopped). observedAt is when the message arrived, never the device’s own clock.

Settings

Editor settings and exact defaults
Setting / propertyDefaultMeaning
Namename · stringEmptyDisplay label.
Brokerbroker · mqtt-brokerNoneNode-RED’s MQTT broker node. With one, the node subscribes to its device’s topics (<prefix>/#) and publishes on them itself: output 1 sends nothing, and the MQTT in and MQTT out nodes around it are no longer needed (still wired, a device message on its input is ignored, with a trace, so nothing is doubled). Its own commands come back through its subscription, as through an MQTT in node before, so it still tells them from someone else’s. It reads its cover on each connect, as a Status node’s startup did through the cover controller. Needed for a new node; opening and saving the node offers the first broker in your flows. A node saved before 6.2 keeps using its MQTT in and out nodes, and needs no broker until you choose one (publishesThroughOutput, with no form row, true for it and cleared when a broker is chosen).
MQTT topic prefixtopicPrefix · stringEmptyRequired. The device’s topic prefix: its device ID unless a custom prefix is set on the device. It cannot contain + or #.
Cover IDchannel · number00, or 1 for a device’s second cover.

On the device, MQTT must be on with Enable MQTT Control (the default), or it ignores the commands. RPC status notifications (also the default) report each change. Calibrate the cover on the device first.

Device topics and payloads

Topics sent and read
TopicDirectionPayload
<prefix>/command/cover:<id>Output 1pos,<0-100> for set_position (rounded and clamped), stop for stop, status_update for observe.
<prefix>/status/cover:<id>ReadThe cover’s full status JSON, including current_pos, state and pos_control.
<prefix>/events/rpcReadNotifyStatus / NotifyFullStatus frames holding cover:<id>.
<prefix>/onlineReadtrue or false.

When only changes have arrived and none carries the position, the node sends status_update to get the full status first.

Availability

<prefix>/online becomes msg.cover = {kind: "availability", online} on output 2. When the device comes back online, the node also sends status_update, since the cover may have moved while it was away.

Uncalibrated or unknown position

The node never makes up a position. A cover that is not calibrated (pos_control false, or no current_pos in a full status) or whose position is unknown (current_pos null) fails the command in hand with {kind: "command_result", ok: false, reason}, reason not-calibrated or position-unknown. A set_position is not sent to an uncalibrated cover, which would refuse it. Reports while the device says calibrating are ignored.

Status

  • waiting for the device (grey ring) until the first status arrives.
  • <state> · <position>% (green), for example stopped · 60%; ? stands for an unknown position.
  • not calibrated (yellow).
