Neutral commands in, Zigbee2MQTT out

The zigbee2mqtt light node (type home-z2m-light; canvas label: its name, its friendly name, or “zigbee2mqtt light”) translates a room lighting controller’s neutral light commands into Zigbee2MQTT’s /set payloads, and the light’s reports into neutral readings. Use one per light in the room’s targets. It also tells the room’s own commands from someone else’s, and skips a restyle the light already shows; both depend on Zigbee2MQTT’s units, so they are done here rather than in the room.

Looking for wiring?

Follow Wire the room. For a light that isn’t Zigbee2MQTT’s, see the neutral light contract.

Outputs

Two output ports
PortMessageConnect to
1 · To the light{topic: "zigbee2mqtt/<device>/set", payload, retain: false}, or /getAn MQTT out node with no topic set.
2 · To the roommsg.light readings: observed, external, echo-changed, skipped, availabilityThe room lighting controller’s input.

An observed reading is {kind: "observed", target, on, brightnessPct?, colorTempKelvin?, fields, showsLast, observedAt}: the values are the light’s, converted back to percent and kelvin; fields lists what it has reported since start (brightness, colorTemp); showsLast says it shows exactly the last command sent, in Zigbee2MQTT’s own units. observedAt is when the report arrived.

Settings

Editor settings and exact defaults
Setting / propertyDefaultMeaning
Name / nameEmptyThe canvas label.
Broker / brokerNoneNode-RED’s MQTT broker node. With one, the node subscribes to its device’s topics (<base>/<friendly name>, its /set and its /availability (exactly these: a friendly name can contain /)) and publishes on them itself: output 1 sends nothing, and the MQTT in and MQTT out nodes around it are no longer needed (still wired, a device message on its input is ignored, with a trace, so nothing is doubled). Its own commands come back through its subscription, as through an MQTT in node before, so it still tells them from someone else’s. It reads its light on each connect (not a group, which Zigbee2MQTT can’t be asked), as a Status node’s startup did through the room. Needed for a new node; opening and saving the node offers the first broker in your flows. A node saved before 6.2 keeps using its MQTT in and out nodes, and needs no broker until you choose one (publishesThroughOutput, with no form row, true for it and cleared when a broker is chosen).

Device payloads

Each command becomes the payload the room controller sent before 6.0, field for field and in the same order: the state, any other fields the intent gave (an effect, say), brightness (1-254, from percent; 0 % is 1, the dimmest), color_temp (mireds, from kelvin), then transition unless the intent set one. An OFF is {"state":"OFF"} alone.

A styled ON, as published
{"state":"ON","brightness":64,"color_temp":400,"transition":1}

A restyle (restyle: true, sent only for a light already on) is not published when the light’s last report already shows exactly those values; the node answers {kind: "skipped", target, id, observedAt} with the time of that report. Any other command is always published.

Its own commands and someone else’s

  • Its own: a command on /set exactly as it sent one in the last 5 seconds, even seen twice.
  • Its own, changed on the way: an ON or OFF arriving while one of its own with that power hasn’t come back, as when a function cut it to {"state":"ON"}: an echo-changed reading, never someone else’s.
  • Someone else’s: anything else: {kind: "external", target, state, setsValues, observedAt}, where setsValues says it sets brightness, colour or an effect. The room may take it as a person’s change.

Groups

A group takes the same commands. Zigbee2MQTT works out a group’s state itself, from what it sent and its members’ reports, so the group’s report follows a command at once. A group has no availability and can’t be asked to report, so it ignores observe: the room waits for Zigbee2MQTT’s next state for the group. Passing on an old state instead could settle a command still on its way. Switch on the group’s retain in Zigbee2MQTT: retain: true under the group in Zigbee2MQTT’s configuration.yaml (it is off by default). Zigbee2MQTT doesn’t retain a group’s state by default, so after a restart the room has no reading for the group until it changes, and an activity that holds it waits on it. With retain, the broker gives the node the group’s last state as soon as its MQTT in node subscribes.

Availability

zigbee2mqtt/<device>/availability becomes {kind: "availability", target, online} on output 2. The room shows it on the light’s control sensor and in its status, and changes nothing because of it. It needs Zigbee2MQTT’s availability setting on.

Status

  • waiting for the device (or group · waiting for its state), grey ring, until the first report.
  • group · no state yet: set retain: true for it in Zigbee2MQTT (yellow ring): a group that has had no state 30 seconds after it started. A group can’t be asked for its state, so without Zigbee2MQTT retaining it there is none until it changes, and an activity holding it reports it unobserved.
  • on · 25% 2500K (green) or off (grey) after a report.
  • offline (grey ring) after an availability message saying so.
