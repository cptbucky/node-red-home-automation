Guides

Run a home theatre

One request, such as “tv” or “off”, drives the display, receiver, media source, room lights and TV backlight together. Each device keeps one owner, and the activity is ready only when every required device has been seen doing what was asked.

Before you wire it

A home theatre is built from seven nodes. Two coordinate the activity, and five each own one kind of device:

The theatre nodes
Palette nameTypeOwns
theatre state contracthome-theatre-state-contractTurns MQTT activity requests into activity intents, and publishes the activity controller’s state as retained MQTT topics, with optional Home Assistant discovery.
theatre activityhome-theatre-activity-controllerThe latest request’s activity: plans each target, collects its evidence and decides when the activity is ready, waiting or failed.
display modehome-display-mode-controllerThe TV, the projector and the projector screen, for the off, tv and projector modes.
AVR controllerhome-avr-controllerThe receiver’s power, main zone, source and bounded volume.
source capability controllerhome-source-capability-controllerWhether a media source is available, active, running an application or playing.
TV backlightinghome-backlighting-controllerThe TV backlight’s power.
activity lightinghome-activity-lighting-controllerThe activity’s style for room lights that are already on, through a room lighting controller.
  • A broker connection in Node-RED, for the request topic and the retained state.
  • A transport for each device the package doesn’t reach itself: a TCP connection for the receiver, and your own adapters for the media source and the projector’s infrared power toggle. For a WLED TV backlight, the wled node is the transport; for another backlight, your own. The display controller reaches the TV and the screen directly over their LAN APIs.
  • A room lighting controller for the lights the activity styles. See Light a room.

Home Assistant is optional. It can show the activity and request one, through the MQTT topics; it is never the path to a device.

How the pieces divide the work

The activity controller sends each target what it should end up as, never how to get there. Each equipment controller keeps its own sequencing, transport, retries and confirmation, and reports back what it observed.

Stale work is inert

Every request gets a generation number. Timers, results and observations carry it, and one from an older request cannot change or complete a newer one.

Readiness is observed

A required target counts only with a fresh report from its device. A command that was sent, or acknowledged, is not a confirmation.

Manual control is kept

A change made by hand becomes a manual override. No controller fights it; the next request takes over again.

Volume has one owner

The receiver controller bounds, sends and confirms volume requests, then lets go, so a later change by hand becomes the new baseline.

Wire the whole set

Requests flow down from the state contract to the equipment controllers. Evidence flows back up from each controller’s output 2 to the activity controller, whose state goes back to the contract for publishing.

After a deploy, send the display and AVR controllers {kind: "startup"} on their own property (msg.display, msg.avr), so they read their devices again rather than trusting saved state. The state contract announces itself once the flows start, and again at msg.theatreStateContract = {kind: "startup"}.

Set the state contract’s Area. With Base topic empty it is required, because it makes the default base topic home/<area>/theatre; a contract saved before node IDs with discovery on needs it too. Otherwise it is optional. The contract in the imported Home theatre activity.json example has no area, so it shows invalid configuration until you set one; put the same area in the request tv activity inject’s topic.

Route commands by target

The activity controller sends msg.theatreCommand = {target, kind, requestId, generation, …}, with kind intent for a new request or refresh to re-confirm, and the activity’s wanted values for that target. Your flow delivers each one to the matching controller: one switch node on msg.theatreCommand.target with five outputs, and a change node per target that moves msg.theatreCommand to the controller’s property.

Where each target command goes
targetMove toControllerWanted values
displaymsg.displaydisplay modemode: off, tv or projector
avrmsg.avrAVR controllerpower (on or standby) and an optional source
sourcemsg.sourceCapabilitysource capability controlleraction (activate or deactivate), sourceId and readiness
lightingmsg.activityLightingactivity lightingprofile: a profile name on the activity lighting node
backlightingmsg.backlightingTV backlightingpower: on or off

In the switch node, set the property to msg.theatreCommand.target and add one == rule per target. In each change node, use Move from msg.theatreCommand to the property in the table.

Describe the activities

Two settings name the activities, and they must agree. The state contract’s Activities JSON lists the names it accepts, such as ["off","tv"]. The activity controller’s Profiles JSON gives each of them every target’s wanted values. Profile names start with a lower-case letter, followed by lower-case letters, digits, _ or -.

theatre activity · Profiles JSON
{
  "off": {
    "display": {"mode": "off"},
    "avr": {"power": "standby"},
    "source": {"action": "deactivate", "readiness": "optional"},
    "lighting": {"profile": "off"},
    "backlighting": {"power": "off"}
  },
  "tv": {
    "display": {"mode": "tv"},
    "avr": {"power": "on", "source": "shield"},
    "source": {"action": "activate", "sourceId": "streamer", "readiness": "required"},
    "lighting": {"profile": "tv"},
    "backlighting": {"power": "on"}
  }
}
  • Every profile names all five targets.

    A profile that leaves one out is an invalid configuration.

  • The source’s readiness decides whether it is waited for.

    required holds the activity at waiting_for_source until the source is confirmed; optional lets the activity be ready without it. An activate needs a sourceId; a deactivate without one acts on the previous activity’s source.

  • Names on the other nodes must exist.

    The AVR’s source is a key in the AVR controller’s Sources (by default {"shield":"SAT/CBL","playstation":"GAME"}), the sourceId a key in the source controller’s Source capabilities, and the lighting profile a key in the activity lighting node’s Profiles JSON.

The activity lighting node’s profiles give targets and values in the package’s own units, for example {"off": {"targets": [], "values": {}}, "tv": {"targets": ["main"], "values": {"brightnessPct": 25, "colorTempKelvin": 2500}}}. It styles only lights that are already on and not manually owned. When it lets go of a light (the activity ends, or a new profile no longer names it), the room lighting controller gives the light back what it was before the activity took it, so it stays on, in the room’s style as it is now. A light a person changed during the activity, which a newer request then took back, gets that person’s values back instead and stays theirs. See owners stack.

Request an activity

Publish a non-retained request on home/<area>/theatre/request, with a new request ID and one of the configured activities. The request ID starts with a letter or digit and continues with letters, digits, ., _, : or -, up to 128 characters.

Inject → theatre state contract · request the tv activity
msg.topic = "home/<area>/theatre/request";
msg.payload = {requestId: "example-request-1", activity: "tv"};
return msg;
  • A new request ID is a new request.

    The contract gives it the next generation, and the newest request wins: the activity in hand is reported superseded.

  • The latest request again is a duplicate.

    Sent again with the same request ID, it is passed on unchanged and starts nothing new. Only the latest request is compared: an older request ID sent again is a new request. Reusing the latest request ID for a different activity is an error.

  • An invalid request is an error on the message.

    An unknown activity or a malformed request ID is reported against the message, where a Catch node can see it.

With Publish set to MQTT state and Home Assistant discovery, the contract adds a Requested activity selector that publishes the same request with a request ID of its own. The topics and payloads are listed in the Theatre MQTT contract.

How an activity completes

The activity controller moves through these phases, shown in its node status as <activity>: <phase>:

  1. preparing

    The request is accepted, earlier target evidence is cleared, and one intent goes to every target.

  2. transitioning

    A required target is changing its device.

  3. confirming

    A required target has not yet reported fresh evidence, or is confirming what it observed.

  4. waiting_for_source

    Every required device is ready, but a source with readiness: "required" is not yet confirmed. This is expected waiting, not a failure.

  5. ready

    The display, receiver and backlight each reported ready within Freshness ms (default 30000), and so did the source if it is required.

Room lighting is optional: a light that is not confirmed (or, with no reading at all by activity lighting’s confirmation timeout, unobserved), or a source with readiness: "optional" that is not, leaves the activity ready with availability degraded and the target listed as degraded, rather than holding it back.

Once ready, the activity controller sends each settled target a refresh at half the freshness window, and each controller answers it from fresh readings. A target that stops answering is asked up to three times, then shown as degraded with reason no-response; it does not undo a ready activity, and it is asked again once per freshness window.

Each equipment controller’s output 2 · target state
msg.theatre = {kind: "target_state", target: "avr", requestId, generation,
  status: "ready", observedAt: "2026-01-01T20:00:01.000Z"};

How an activity fails

A required target (display, receiver or backlight) that reports failed or unavailable fails the whole activity: the phase becomes failed, the current activity unknown, and the status shows <activity>: <reason>. The failure names the target, the operation and the reason the target gave, or unavailable or target-failed when it gave none.

Common failure and rejection reasons
ReasonFromWhat it means
no-readingdisplay modeA device didn’t report within Query timeout milliseconds, after Maximum idempotent attempts. The failure names the device.
screen-not-calibrateddisplay modeA Screen viewing position is set, but the screen has no position. See the screen viewing position.
no-responsetheatre activityA target never answered the activity controller’s refreshes before the activity first completed.
stale-generation, request-conflict, generation-conflicttheatre activityA request was rejected: it was older than the one in hand, or reused its request ID or generation for something else.

A failed activity stays failed until the next request. Fix the cause, then request the activity again with a new request ID.

Manual overrides and recovery

When someone changes the display, receiver, source, backlight or a room light the activity holds by hand after an activity is ready, that controller reports a manual override instead of sending a correcting command. The activity controller’s phase becomes manual_override, with availability degraded. A newer request takes over again.

  • Restart with saved state.

    Node-RED keeps a node’s state across a restart only with a context store configured; see the README’s file context store setup. A controller then re-reads its devices rather than replaying old commands.

  • Restart with nothing saved.

    The activity controller has no activity: its phase is idle and its current activity unknown, and nothing is commanded until the next request, so a redeploy never switches a running activity off. A msg.theatre = {kind: "startup"} puts it in recovering and sends every target a refresh with no request. The display, AVR, source and backlighting controllers answer it with what their devices show, and when that matches exactly one activity, the theatre adopts it (event recovery_adopted), ready, with nothing commanded. A device that can’t be asked, such as a backlight that only reports when it changes, needn’t answer: once the refreshes run out (about one and a half freshness windows), the theatre adopts from the ones that did, as long as the display and the receiver are among them, and shows the silent one as unobserved until it reports. When the answers match none, or more than one, or the display or the receiver doesn’t answer, it returns to idle and unknown (event recovery_unknown): send a request to take over again.

  • A target that restarted alone.

    It takes the activity’s wanted values from the next refresh and only reads its device: ready if the device already matches, or a manual override with reason adopted-mismatch if it doesn’t, sending nothing until the next request.

Ask the receiver for a volume

Send volume requests to the AVR controller rather than receiver commands. Volume is in dB: valueDb is the level for absolute, or the change for relative.

Inject → AVR controller · one step louder
msg.avr = {kind: "volume", requestId: "volume-control-1", mode: "relative", valueDb: 1};
return msg;
  • dB and the receiver’s 0-98.

    The controller converts for the receiver: on its 0-98 scale, 80 is 0 dB, so the range is -80 to +18 dB in half steps. A reading of MV30 is -50 dB.

  • Bounds.

    Every request is held within Minimum volume (dB) and Maximum volume (dB) (defaults -80 and -20).

  • Rapid requests add up.

    A relative request starts from the fresh observed volume, or from the target still pending. Two quick +1 dB steps from -50 dB send -49 dB, then -48 dB.

  • Confirmed, then released.

    A fresh receiver reading confirms the request (volume_ready), and the controller lets go: a later change at the receiver is reported as volume_external and becomes the new baseline, not corrected.

  • 0-98 values are gone.

    A request with value in the receiver’s 0-98 and no valueDb is answered volume_rejected with reason removed-volume-value, with a warning in the log. A node saved with only the old 0-98 minVolume and maxVolume is an invalid configuration until its dB bounds are set.

  • Activities own power and source, not volume.

    A volume request waits while an activity is switching the receiver’s power or source, and is rejected with receiver-not-ready while the receiver is off. One still pending at a restart is reported volume_failed with reason restart.

With Publish set to MQTT state and Home Assistant discovery, Home Assistant gets a volume number in dB. Its sets arrive on home/<area>/receiver/volume/set: with a Broker, the AVR controller reads them itself; without one, wire an MQTT in node on that topic into it. Sets within 0.3 seconds of each other are settled to the last, which becomes an ordinary absolute request.

Report projector power from a meter

The display controller needs a fresh projector power reading at every request and while it confirms a change. With Projector power meter host set, it reads a Shelly Gen2 switch with power metering on the projector’s supply itself. Left empty, your flow reports the power from any meter or adapter:

Your meter → display mode controller
msg.display = {kind: "observed", device: "projector", watts: 140};
// or, from an adapter that knows the lamp state:
msg.display = {kind: "observed", device: "projector", power: "on"};
  • Watts are read against two thresholds.

    Projector on watts (default 20) and Projector standby watts (default 10). Between them, the lamp keeps its last settled state while it warms or cools.

  • Power is lower case.

    "on", "standby" or "transitioning". A smart plug’s own ON and OFF are the socket, not the lamp: send its watts instead. observedAt and source are optional.

  • Output 3 asks for a reading.

    When the controller needs one, it sends msg.payload = "query" on output 3. Wire it to whatever makes your meter report, such as a Zigbee2MQTT plug’s zigbee2mqtt/<device>/get topic. Leave it unwired only if the meter reports on its own at least once every Query timeout milliseconds (default 5000), even while the power holds steady.

  • No reading fails the request.

    A device that hasn’t reported is asked again, up to Maximum idempotent attempts (default 2) in all, then the request fails with reason no-reading. Keep Transport timeout milliseconds below the query timeout × the attempts.

The projector itself is switched by its power toggle on output 1 (msg.payload = "power" with msg.display_command): wire it to your infrared transport.

Set the screen viewing position

For projector mode, the display controller opens the screen, a Shelly Gen2 cover at Screen controller host, after the projector has warmed up. Switching between TV and projector is make before break, so a playing source keeps a picture.

  • Empty (the default for a new node).

    The screen’s own open command, confirmed when the screen reports itself fully open. This also suits a screen that isn’t calibrated for positions.

  • A position above 0, up to 100.

    The percentage of its travel to open to, confirmed within Screen position tolerance (default 2). A screen that doesn’t know its position is closed first; if it still has none, the request fails with screen-not-calibrated. Calibrate the screen, or clear the setting.

  • Other modes close it.

    With the screen’s own close, which runs to the end and restores a position the screen has lost.

A node saved with a position keeps it.

Check the result

Wire Debug nodes to the state contract’s output 2 and to each equipment controller’s output 2, then watch the node statuses.

Activity status none: idleNo request since start, or the activity couldn’t be recovered. Send a request.

A controller shows invalid configurationA required setting is missing: the contract’s area, or the display controller’s hosts and TV pre-shared key. The activity waits for that target.
