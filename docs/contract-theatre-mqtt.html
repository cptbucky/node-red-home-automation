Theatre MQTT contract

The topics, payloads and guarantees of the whole-theatre MQTT contract: one request topic in, retained state topics out, and an optional Home Assistant panel.

home-theatre-state-contractMQTT contracthome theatre

One request in. Retained state out.

The theatre state contract node bridges the theatre activity controller to MQTT and, optionally, Home Assistant, without moving policy into flow wiring. It accepts activity requests on one topic, passes them on as intents, and publishes each controller snapshot as retained state topics.

Looking for wiring?

Follow the Home theatre guide for the full flow, and Home Assistant for the optional panel.

Public contract

Each surface of the contract carries a fixed shape and keeps one invariant.

Desired stateActivity and generationOne current request identity

Base topic

Every topic sits under one base topic. With the contract node's Base topic setting empty, it is home/<area>/theatre, made from the node's Area; set it to use any concrete MQTT topic instead. Leading and trailing slashes are dropped, and wildcards (+, #) are refused. Below, <base> stands for it.

Request

Send requests to <base>/request, not retained. The payload is a JSON object (a string or buffer is parsed as JSON):

Request · <base>/request
{
  "requestId": "movie-0001",
  "activity": "movie",
  "requestedAt": "2026-01-01T20:00:00.000Z"
}
Request fields
FieldRule
requestIdRequired and unique per request: starts with a letter or digit, then up to 127 letters, digits, ., _, : or -. Repeating the latest request's ID with the same activity is a duplicate, not a new request; reusing it for another activity is an error. Only the latest request is compared: an older ID sent again is a new request.
activityRequired; must be one of the activities configured in the contract's Activities JSON.
requestedAtOptional ISO timestamp; when absent, the time of receipt.

A new request takes the next generation and resumes automation. On acceptance the contract publishes desired, sets phase to requested, clears failure and sets readiness to unknown until the controller reports.

Retained requests are inert

A request that arrives retained is ignored and traced as retained-request, so a broker replaying an old request never starts an activity. Command and request topics must not be retained.

Retained state topics

Every publication below is retained, so a restarted subscriber rebuilds the theatre's state at once. A snapshot from an older generation than the current request is ignored as stale-generation. Each topic is published only when its payload changes, leaving aside the fields that only say when or how long ago something was seen (observedAt, evaluatedAt, and in metrics each target’s observationAgeMs): a steady activity whose targets keep re-confirming publishes nothing new, so Home Assistant records no change for every refresh. A target’s health therefore keeps the time it last changed, not the time it was last confirmed; a target that stops answering is still shown, as readiness going degraded with the target named stale or no-response in transition. Each startup, and with a Broker each connect, publishes every topic again with the next snapshot, in case the broker lost them.

Display, AVR and backlighting are mandatory targets; lighting is optional, so its failure degrades a transition instead of failing it.

Readiness and availability

These are two different questions on two topics.

  • <base>/readiness says whether the theatre is ready: unknown, available, degraded or unavailable. Ready requires all mandatory targets. Before 4.0 this value was on <base>/availability.
  • <base>/availability says whether the contract node is running: online once the flows have started, offline as it stops. Home Assistant shows the theatre entities as available only while it is online.

On a full deploy, a restart or a shutdown, Node-RED closes the broker connection at the same moment, so set the MQTT broker node's Birth message to online and its Close message and Will message to offline, all retained, on <base>/availability.

Metrics

<base>/metrics exposes transition latency and outcome counts plus per-target evidence. Before the first snapshot it carries zeros:

Metrics · <base>/metrics
{
  "requests": 0,
  "ready": 0,
  "failed": 0,
  "superseded": 0,
  "manualOverrides": 0,
  "driftEvents": 0,
  "recoveriesAdopted": 0,
  "recoveriesUnknown": 0,
  "lastTransitionMs": null,
  "maxTransitionMs": null,
  "lastOutcome": null,
  "targets": {}
}

Under targets, each target carries retry, fallback, confirmation-latency, failure, manual-override and availability evidence. Its lastConfirmationMs is how long after the transition started the target first reported ready; its refreshes leave it, and the next transition times it again.

Operational objective

The contract keeps a bounded window of transition outcomes and publishes the success rate and the p50 and p95 transition latency on <base>/slo, with a status and a reason. A ready outcome whose transition wasn’t timed counts towards the success rate but not the latency, and stays untimed after a restart.

Observation time and clock skew

Each target report the activity controller receives (msg.theatre with kind: "target_state") must carry an ISO observedAt, and only reports for the current generation count; others are ignored as stale-generation.

A report time more than one second ahead of Node-RED's clock is treated as observed on receipt and traced as clock-skew, so one device with a wrong clock cannot hold back later reports. A report older than the target's latest one is ignored as out-of-order, so older evidence never overwrites newer evidence.

Manual ownership

Unsolicited display, AVR, source and backlighting changes latch manual ownership instead of issuing corrective commands. A newer explicit activity request resumes automation.

A target controller that starts with nothing saved (a redeploy or restart without a context store) takes the activity's wanted values from the activity controller's next refresh and only reads its device: it reports ready when the device already matches, and a manual override with reason adopted-mismatch when it doesn't, sending no command until the next request.

Recovery

After a redeploy or restart with nothing saved, the activity controller has no request: the activity is unknown and nothing is commanded until the next request, so a redeploy or restart never switches a running activity off. The controller does not adopt an activity from the devices on its own: adopting one needs a recovery message carrying observations, and the controller's own fallback, when its recovery refreshes run out, recovers with no observations (traced no-observations), which leaves the activity unknown.

After a cold start

The activity controller asks every target what its device shows and adopts the one activity that matches, if any, without commanding anything; the contract then publishes it as for any ready activity.

While it is unknown, <base>/phase shows idle (the controller isn't working on anything) and <base>/current shows unknown until the next request, even if something is playing.

Home Assistant entities

With Home Assistant discovery on, the contract announces these entities under the discovery prefix once the flows start, before online, and again at a startup event; switched off, the next startup event clears them. They read the topics above and follow <base>/availability. Home Assistant is an optional panel, never the device path. See Home Assistant.
