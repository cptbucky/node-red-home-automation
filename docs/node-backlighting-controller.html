Backlighting controller

Message shapes, output ports and settings for TV backlight power. A command acknowledgement never counts as the backlight being on or off.

On this pageOn or off, confirmed by a reading.InputsOutputsSettingsRetries, failure and manual changesStatus
home-backlighting-controller1 input · 2 outputshome automation

On or off, confirmed by a reading.

Owns the power intent of a TV backlight (bias lighting behind the screen) with bounded command retries. It is confirmed only when the device reports the wanted power. Your flow’s transport switches the device and reports its power back; for a WLED strip, the wled node is that transport.

In the palette it is backlighting controller under home automation; on the canvas it shows its name, or TV backlighting when unnamed.

Looking for wiring?

Follow Home theatre, where the theatre activity controller sends this node its backlighting commands. Backlighting is a required target: an activity isn’t ready until it confirms.

Inputs

Every input is msg.backlighting with a kind.

msg.backlighting kinds
kindOther fieldsUse
intentrequestId, generation, power, optional requestedAtRequest power on or off; generation is a positive integer.
observedgeneration, power, observedAtThe device’s reported power. A reading older than the request is ignored.
command_resultgeneration, ok, optional reasonThe transport’s result. ok: true starts confirmation; it is not confirmation.
refreshoptional requestId, generation, powerFrom the theatre activity controller: re-read a settled backlight, or adopt the activity’s wanted power after a start with nothing saved. With no request (requestId null, generation 0: the activity controller’s probe after a start with nothing saved) and none of its own, it sends observe (with requestId null, generation 0 and no power; an observation with any generation answers it), then answers on output 2 with msg.theatre = {kind: "target_observation", target, observedAt, values}, where values is {power}, and commands nothing.
startupNoneRe-read the device for the request in hand; never replays the command.
tickgenerationSent by the node itself on its timer.
Intent · msg.backlighting
{
  kind: "intent",
  requestId: "example-backlighting-1",
  generation: 1,
  power: "on"
}

Outputs

The port order is fixed.

Two output ports
PortMessageConnect to
1 · Backlighting commandsmsg.backlightingCommand = {operation, requestId, generation, power, attempt}; operation is set_power or observe.Your backlight transport, which answers with command_result and observed messages.
2 · Theatre target statemsg.theatre = {kind: "target_state", target: "backlighting", requestId, generation, status, observedAt, details}, with classification and failure when set.The theatre activity controller’s input.

details holds the wanted power, the observedPower, recovery and metrics (attempts, retries, fallbackUsed).

Settings

Defaults below are from the editor definition. Timing values are in milliseconds.

Editor settings and exact defaults
Setting / propertyDefaultMeaning
Namename · stringEmptyDisplay label.
Areaarea · stringEmptyOptional label; empty means no area.
Poll mspollMs · number2000How often to send observe while confirming.
Confirm msconfirmationTimeoutMs · number15000How long one attempt may take to confirm.
AttemptsmaxAttempts · number2Power commands before failing.

Retries, failure and manual changes

An intent sends set_power, then polls with observe until the reported power matches. A failed command_result or a confirmation timeout resends set_power until Attempts, then fails with the transport’s reason, command-failed or confirmation-timeout.

A different power reported after the backlight was ready is a person’s change: it is reported as manual_override and never corrected until the next request. A ready backlight is re-read on refresh without leaving ready.

Status

The node status reads <power>: <phase>, with none when no request is in hand.
