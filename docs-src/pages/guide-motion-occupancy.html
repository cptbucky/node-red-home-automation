Before you wire it

Two nodes sit between your sensors and the room lighting controller. The occupancy fusion node (home-occupancy-fusion in the palette, shown on the canvas as “occupancy”) combines motion and optional presence into one occupied or vacant event. The motion lighting policy (home-motion-lighting-policy, shown as “motion policy”) turns occupancy and light level into lighting intents for the room lighting controller.

Motion establishes occupancy. Presence, such as an mmWave sensor, can hold occupancy that motion established, but never establishes it by itself. Both nodes read the sensors’ own MQTT messages, for example from Zigbee2MQTT; Home Assistant is not in the path.

Each message names its kind in msg.source. The payload can be a plain value or an object:

Sensor messages
SensorSend tomsg.sourcemsg.payload
Motion (PIR)occupancy fusion"motion"true/false; "on", "occupied", "active", "detected" or their opposites "off", "clear", "inactive", "not_detected"; or an object with a motion, occupancy or active field.
Presence (optional)occupancy fusion"presence"The same values, or an object with a presence, occupancy or active field. Ignored unless Presence sensor is set to hold.
Light level (optional)motion lighting policy"illuminance"A number in lux, or an object with an illuminance or illuminanceLux field.

A value the node can’t read as on or off is ignored. Without any illuminance reading, the policy treats the room as dark enough. Wall switches go to the switch lighting policy, not here: see Wall switches.

Wire sensors to the room controller

Occupancy flows one way: sensors into occupancy fusion, its events into the motion policy, and the policy’s intents into the room lighting controller, which owns the light commands.

Occupancy fusion sends occupied: true on every motion edge from off (or not yet seen) to on, even when the room is already occupied, as happens when presence held it between motion reports; each one makes the policy cancel its countdown and, if enabled and dark enough, send ON again. Only a repeated motion-on while motion is still on is dropped. Motion going off sends occupied: false unless presence is holding the room, and the first motion reading the node has seen (nothing saved yet) sends it if it is off, even when the room is already vacant.

  1. Choose the presence mode.

    On occupancy fusion, Presence sensor defaults to “None (PIR only)”. Choose “Hold occupancy (PIR + mmWave)” if you wire a presence sensor in.

  2. Name the lights.

    ON targets and OFF targets on the motion policy are JSON arrays of target ids from the room controller’s Targets JSON. Both default to ["main"], the target id in the example flow.

  3. Set the vacancy time and lux cutoff.

    See Vacancy delay and other settings below.

Vacancy delay and other settings

When occupancy turns on, the policy cancels any pending switch-off and, if motion lighting is enabled and the light level is at or below the cutoff, sends ON to the ON targets. When occupancy turns off, it starts a countdown of Vacancy seconds; when that runs out it sends OFF to the OFF targets.

Motion policy settings
SettingDefaultWhat it does
ON targets["main"]Lights switched on when the room becomes occupied.
OFF targets["main"]Lights switched off when the vacancy time runs out.
Vacancy seconds120How long the room stays vacant before the OFF intent.
Lux cutoff10The brightest light level, in lux, at which occupancy still switches lights on.
Maximum pause (s)600How long a pause lasts unless sent again.

Other flows can change the vacancy time and cutoff without opening the editor:

Function → motion policy · change the vacancy time
msg.source = "delay";
msg.payload = 300; // seconds, the same unit as Vacancy seconds
return msg;
Function → motion policy · change the lux cutoff
msg.source = "illuminance-cut-off";
msg.payload = 20;
return msg;

A delay or illuminance-cut-off message overrides the setting until a deploy changes Vacancy seconds or Lux cutoff in the editor; the new setting then applies. Keeping the override across a restart or redeploy needs a file context store.

Switch it off, or pause it

The motion policy has two ways to stop acting on occupancy. They look alike but belong to different people.

Enable versus pause
msg.sourcePayloadWho it is for
"area-enabled"true or falseThe user’s own switch for this node’s motion lighting. It stays as set, and is what the Home Assistant motion lighting switch shows and sets.
"global-enabled"true or falseThe user’s switch for every motion policy at once. It is not published.
"pause"true pauses, false releases; msg.owner is requiredOther flows, such as a moving cover. Each owner holds its own pause, and motion lighting resumes once every owner has released it or its pause has run out (Maximum pause, sent again to renew).

Motion lighting acts only while both enables are on and no owner holds a pause. Switching it off or pausing it cancels a pending vacancy countdown. If the room goes vacant meanwhile, the countdown starts when motion resumes, so lights left on during a pause, an activity or a scene still go off in an empty room.

Cover controller output 3 → Function → motion policy · pause while moving
msg.source = "pause";
msg.owner = "study blind"; // a name of its own for each pauser
return msg; // keep the boolean payload
Never pause with the enable.

A pause never changes the enables, which are the user’s own. A flow that sends area-enabled false to pause motion overwrites what the user chose, and can leave motion lighting off for good if the true never comes. See Wire a cover.

When a person changes a light

The OFF intent carries vacantSince, the time the room went vacant. The room lighting controller keeps on any light a person set after that time: they are using it, so motion doesn’t switch it straight off.

  • A light a person set before the room went vacant is still switched off when the vacancy time runs out.
  • A light another owner holds, such as an activity or a scene, is left alone by motion ON and OFF; its other targets are still handled.
  • Switching a light from a wall switch goes through the switch policy, which marks the press as a person’s.

Your flow decides who a request is from; the room controller doesn’t guess, and values alone don’t count as a person’s change. When a request comes from a person, for example a dashboard slider, set person: true (or manual: true) on the intent you send the room controller. A light set that way after the room went vacant stays on when motion’s OFF arrives.

Function → room controller · a dashboard slider, from a person
msg.lighting = {
  kind: "intent",
  targets: ["main"],
  state: "ON",
  values: {brightnessPct: msg.payload},
  person: true
};
return msg;

The room controller’s control states are described in Room light control in the README.

Without a context store, a restart forgets who is in the room.

A motion policy that starts with nothing saved (its first deploy, or a redeploy or restart without a context store) counts the room as vacant from then. Unless occupancy is reported within Vacancy seconds, it sends its OFF intent, so someone sitting still in a lit room has the lights switched off unless motion is seen. The room controller has also forgotten which lights a person set. A file context store keeps both; a running countdown then carries on.

Show it in Home Assistant (optional)

Both nodes can publish their state over MQTT, through their Broker (or, without one, on their second output). Publishing is off until you switch it on, and then the node needs an Area; topics use it in lowercase, with spaces and other characters as _. Choose its Broker and it publishes itself (without one, wire output 2 to an MQTT out node).

What each node publishes
NodeTopicsWith Home Assistant discovery
occupancy fusionRetained ON/OFF on home/<area>/occupancy/state; online/offline on home/<area>/occupancy/availabilityAn occupancy binary sensor
motion policyRetained ON/OFF on home/<area>/motion/enabled/state; the vacancy delay in seconds on home/<area>/motion/delay/state; online/offline on home/<area>/motion/availabilityA motion lighting switch and a vacancy delay number

While it publishes (Publish set to MQTT state or more), the motion policy also acts on ON/OFF sent to home/<area>/motion/enabled/set and a delay of 0 to 86400 seconds sent to home/<area>/motion/delay/set, rounded to whole seconds, as the area-enabled (with true or false) and delay inputs do. Retained messages on these topics are ignored. With a Broker it reads them itself. Without one, to let the Home Assistant switch and number control it, wire an MQTT in node subscribed to home/<area>/motion/+/set into the motion policy.

The switch shows this node’s enable only, so motion lighting can still be off everywhere through global-enabled while it shows on. Discovery comes with the MQTT state (Publish set to MQTT state and Home Assistant discovery), and the Discovery prefix defaults to homeassistant. Each node announces itself once the flows have started, and again when it receives msg.source = "startup". More in Home Assistant.
